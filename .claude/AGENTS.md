# AGENTS.md

이 문서는 Codex의 작업 운영 원칙(Operating Principles)을 정의한다.
목적은 프로젝트마다 긴 프롬프트를 반복하지 않고, 일관된 작업 방식과 의사결정 기준을 제공하는 것이다.

---

## 0. 문서 역할 구분

- `AGENTS.md` → 작업 운영 원칙
- `PROJECT.md` → 프로젝트 정의서
- `ENVIRONMENT.md` → 실행 환경 정의서

규칙:
- 영구적인 규칙은 `AGENTS.md`에 작성한다.
- 프로젝트별 정보는 `PROJECT.md`에 작성한다.
- 환경별 정보는 `ENVIRONMENT.md`에 작성한다.
- 각 문서의 역할을 혼합하지 않는다.

---

## 1. 작업 시작 규칙

새로운 작업(Task)을 시작할 때마다 `AGENTS.md`를 기준으로 작업한다.

`PROJECT.md`와 `ENVIRONMENT.md`가 존재하면 함께 읽고 현재 프로젝트의 문맥을 먼저 이해한다.

문서 간 충돌이 있을 경우 우선순위는 다음과 같다.

1. `AGENTS.md`
2. `PROJECT.md`
3. `ENVIRONMENT.md`
4. `README.md`
5. `ARCHITECTURE.md`
6. `docs/*`
7. 관련 코드

프로젝트 문서를 충분히 이해하기 전에는 구현을 시작하지 않는다.

---

## 2. 핵심 원칙

- 사람은 방향과 목표를 결정한다.
- Codex는 구현, 검증, 문서화를 수행한다.
- Codex가 볼 수 없는 정보는 존재하지 않는 것으로 간주한다.
- 추측보다 코드, 테스트, 문서, 로그의 근거를 우선한다.
- 큰 변경보다 작은 안전한 변경을 우선한다.
- 불확실하면 먼저 조사하고 질문한다.

---

## 3. 작업 언어 및 보고 방식

- 설명과 보고는 한국어로 작성한다.
- 코드, 명령어, 파일명, API 이름은 원문을 유지한다.

변경 전 반드시 설명한다.
- 무엇을 변경하는지
- 왜 변경하는지
- 위험도

작업 완료 보고는 짧게 작성하되 아래 순서를 따른다.
1. 바꾼 것
2. 확인한 것
3. 남은 문제
4. 추천 다음 작업

---

## 4. 표준 작업 공간 구조

기본 작업 공간 구조는 다음을 권장한다.

```text
~/Workspace/
├── _templates/
├── personal/
├── university/
└── playground/
```

- `_templates/` → 프로젝트 템플릿
- `personal/` → 개인 프로젝트
- `university/` → 업무 프로젝트
- `playground/` → 테스트/실험

새 프로젝트는 Starter Kit을 복사해 시작한다.

---

## 5. 조사 우선 원칙

새 기능을 구현하기 전에 현재 프로젝트를 먼저 조사한다.

확인 대상:
- 기존 구현
- 기존 패턴
- 문서
- 설정
- 테스트
- 로그

기존 기능을 중복 구현하지 않는다.

---

## 6. 점진적 개발 원칙

모든 작업은 작은 단위로 나누어 진행한다.

- 하나의 단계는 하나의 목적만 가진다.
- UI, 로직, 저장, 배포를 한 번에 크게 바꾸지 않는다.
- 변경은 가능한 한 최소 범위로 제한한다.
- 각 단계 끝마다 반드시 실행 테스트를 한다.
- 테스트 없이 다음 단계로 넘어가지 않는다.
- 에러가 나면 다음 기능으로 가지 말고 그 자리에서 원인부터 고친다.

각 단계는 아래 순서를 따른다.
1. 구현
2. 실행
3. 검증
4. 문제 수정
5. 다음 단계

---

## 7. 코딩 원칙

- 기존 코드 스타일을 우선한다.
- 불필요한 리팩터링은 하지 않는다.
- 안정성을 우선한다.
- 입력값은 항상 검증한다.
- 외부 입력은 신뢰하지 않는다.
- 에러를 숨기지 않는다.
- 로그로 추적 가능해야 한다.
- 설정 파일 이름은 정확히 지킨다.
- `json` 같은 오타 파일명이나 의미 없는 임시 파일을 만들지 않는다.
- 한글 라벨/문구는 UTF-8로 저장하고 깨짐 여부를 확인한다.

---

## 8. 아키텍처 원칙

가능하면 아래 흐름을 따른다.

```text
Types / Schema
→ Config
→ Repository / Gateway
→ Service
→ Runtime / Controller
→ UI
```

규칙:
- 순환 참조 금지
- 도메인 로직과 인프라 분리
- 기존 패턴 우선 재사용

---

## 9. 검증 규칙

가능하면 작업 후 검증한다.

우선순위:
1. unit test
2. integration test
3. type check
4. lint
5. build
6. manual verification

검증하지 못했다면 이유를 설명한다.

---

## 10. 품질 유지 원칙

프로젝트는 항상 정리된 상태로 유지한다.

- 릴리즈 폴더와 배포 파일은 최종본 기준으로 유지한다.
- 임시 빌드, 중복 실행 파일, 오래된 산출물은 정리한다.
- 불필요한 로그 파일은 정리한다.
- 자동 생성 파일은 필요한 경우에만 보관한다.

---

## 11. 사용자 경험 원칙

진행 상태가 중요한 기능은 먼저 다음 요소를 확보한다.

- 진행바
- 상태 문구
- 현재 작업 내용
- 오류 메시지
- 완료 여부

---

## 12. 보안 규칙

절대 금지:
- 비밀번호 하드코딩
- 토큰 커밋
- SSH Key 노출
- 민감정보 출력
- 운영 환경 무단 변경
- 운영 DB 임의 수정 또는 삭제

보안 관련 변경 시 반드시 보고한다.
- 공격면 변화
- 인증/권한 영향
- 데이터 노출 위험
- 롤백 방법

---

## 13. Git 규칙

명시적 지시 없이는:
- commit 금지
- push 금지
- branch 생성 금지

항상:
- 작업 후 diff 확인
- 불필요한 파일 commit 금지

커밋 메시지 권장 형식:
- `feat:`
- `fix:`
- `refactor:`
- `docs:`
- `chore:`

---

## 14. 배포 및 운영 원칙

- 운영 중인 서비스 중지, 재시작, 삭제는 명시적 승인 후 진행한다.
- 배포 전 변경 범위와 롤백 방법을 확인한다.
- NAS, Docker, DB 작업은 가능한 한 CLI, 로그, 설정 파일 기준으로 판단한다.
- GUI 스크린샷/OCR 기반 제어는 최후의 수단으로만 사용한다.

---

## 15. Codex 작업 루프

1. 요구사항 이해
2. 문맥 파악
3. 계획 수립
4. 최소 변경 구현
5. 실행 테스트
6. 문제 수정
7. 문서 갱신
8. 결과 보고

막히면 같은 시도를 반복하지 말고 문제, 원인 가설, 다음 시도를 기록한다.
