# 확장 슬라이드 패드(CPP) — 남의 세이브를 배포하지 않는 방법 (2026-08-18)

> **2026-08-19 정정.** 이 문서의 33바이트 프로파일은 **불완전했다**. 게임 코드를
> 읽어 보니 CPP "켜짐"은 세 가지로 이루어진다 — 컨트롤 표 + **게이트 비트
> (세이브 `0x0C` bit0)** + **프리셋 번호(`0x13C` = 3)** — 그리고 `0x0010AEC0`의
> 강제 루틴이 게이트 비트가 꺼진 세이브를 preset[0]으로 **되돌린다.** 표만 쓰면
> 런타임에 무효화된다는 뜻이다. 도구는 세 가지를 모두 쓰도록 고쳤고, 아래 §2·§4의
> "0x3C..0xF7 33바이트"·"옵션 블록 5바이트" 서술은 그만큼 낡았다. 근거와 정정
> 내용은 [`cstick-default-scheme-feasibility-2026-08-19.md`](cstick-default-scheme-feasibility-2026-08-19.md)
> §1·§4에 있다. 그 외(캡처 절차, 왕복 검증 방법)는 그대로 유효하다.
>
> **배포 방침은 폐기됐다(§6).** 2026-08-19 확정: 에뮬용 산출물이 `code.bin` 24바이트
> 패치로 CPP를 켜고(Azahar 성공 확인), **세이브 패처는 배포물이 아니라 내부
> 개발·검증 도구로 남는다.** RT37 세이브 동봉안도 배포 계획에서 빠졌다.
> 현행 방침은 [`RELEASE-PACKAGING-POLICY.md`](RELEASE-PACKAGING-POLICY.md)다.

배포물에 RT37의 세이브를 동봉해야 한다는 부담을 없애기 위해, **세이브를 갈아끼우는
대신 플레이어 자신의 세이브에서 CPP를 켜는** 방식을 도구로 구현했다.
`tools/mgs3d_save_tool.py`에 `enable-cpp` / `disable-cpp` / `learn-cpp` 추가.

전제는 그대로다. 이 먹통은 우리 패치와 무관하고
([`citra-extrapad-applet-freeze-2026-08-17.md`](citra-extrapad-applet-freeze-2026-08-17.md)),
원본 게임도 Citra에서 똑같이 멈춘다. 고칠 수 있는 것은 **게임 안에서 옵션을 켜지
않아도 되게 만드는 것**뿐이다.

## 왜 세이브 동봉이 걸리는가

| | RT37 세이브 3개 동봉 | 세이브 패처 |
|---|---|---|
| 진행도 | **초기화된다** (전부 게임 첫 지점) | **그대로 유지** |
| 저작권 | 남의 결과물 재배포 + 출처 표기 필요 | 우리 코드만 배포 |
| 사용자 혼란 | "Normal/Hard/Extreme 중 뭘?" | 없음 (자기 파일 하나) |
| 되돌리기 | 불가 | `disable-cpp`로 원상복구 |
| 검증 상태 | 실사용 사례 있음(2021년, Citra) | **정적 검증만 끝. 에뮬 실동작 미확인** |

마지막 줄이 현재의 유일한 약점이다. 아래 §5를 끝내면 사라진다.

## 1. 사용법

```
# 플레이어 자기 세이브에 CPP 켜기 (.bak-cpp 백업 자동 생성)
python tools/mgs3d_save_tool.py enable-cpp "%APPDATA%\Azahar\sdmc\Nintendo 3DS\<0…0>\<0…0>\title\00040000\00081e00\data\00000001\savedata"

# 되돌리기 — 실기에서 잘못 켜서 에뮬에서 못 끄게 됐을 때도 이걸로 끈다
python tools/mgs3d_save_tool.py disable-cpp <savedata>

# 미리보기만
python tools/mgs3d_save_tool.py enable-cpp <savedata> --dry-run
```

쓰기 전에 스스로 검사한다 — 20,768 B인지, 입력 CRC가 맞는지, **프로파일 밖 바이트가
하나라도 바뀌었는지**(바뀌면 중단), 결과가 실제로 원하는 상태인지. 헤더 CRC는
자동 재계산한다. 이미 원하는 상태면 아무것도 쓰지 않는다.

## 2. 어떤 바이트를 쓰는가 — 근거

세이브 5개의 **그룹 차분**으로 구했다. CPP-off 2개(이 프로젝트의 Citra·Azahar
세이브)와 CPP-on 3개(RT37 Normal/Hard/Extreme). 다섯 개 전부 `v001a` / `r_sna01`,
즉 게임 첫 지점이라 진행도 잡음이 작다.

- **각 그룹 안에서 상수**이고 **그룹 사이에서 다른** 바이트: **58개**
- 그중 **33개**가 `0x3C..0xF7` 안에 있다 → 이것이 기본 프로파일이다

| 범위 | 정체 | off → on |
|---|---|---|
| `0x3C` | 컨트롤 스킴 id | `80` → `02` |
| `0x40..0xBF` | 주 버튼 매핑 표 (32 × u32 HID 마스크) | `R→ZR`, `L→ZL`, `ZL→L`, `ZR→R`, `Up→X`, `0x7C..0x88`(X/B/Y/A) 소거 |
| `0xC0..0xF7` | CPP 전용 표 14 entry | **전부 0** → 전부 채워짐 |

`0xC0..0xF7`이 CPP 상태의 가장 깨끗한 지표다(off일 때 전 구간 0). 도구의
`cpp_enabled()`가 이걸 본다.

## 3. 정적 검증 — 전부 PASS

```
python tools/mgs3d_save_tool.py enable-cpp  user_off.sav -o user_on.sav
python tools/mgs3d_save_tool.py disable-cpp rt37_on.sav  -o rt37_off.sav
```

| 검사 | 결과 |
|---|---|
| 5개 세이브 전부 CRC OK (패치 후에도) | **PASS** |
| 사용자 세이브에 enable → `0x3C..0xF7`가 RT37 CPP-on과 **바이트 동일** | **PASS** |
| RT37에 disable → `0x3C..0xF7`가 진짜 CPP-off 세이브와 **바이트 동일** (Normal·Hard·Extreme 3/3) | **PASS** |
| 창 밖 바이트 변경 수 (진행도 보존) | **0** |
| on → off → on 왕복이 원본과 바이트 동일 (Normal·Hard·Extreme 3/3) | **PASS** |
| off → on → off 왕복이 원본과 바이트 동일 | **PASS** |
| 이미 켜진 세이브에 enable | 아무것도 쓰지 않음 |

세 번째 줄이 핵심이다. **다른 콘솔·다른 플레이스루**의 CPP-on 세이브를 끈 결과가
실제 CPP-off 세이브와 바이트 단위로 같다는 것은, 이 33바이트가 플레이어별 값이
아니라 **게임이 두 상태에서 쓰는 고정된 표**라는 뜻이다.

## 4. 아직 증명되지 않은 것 — 정직하게

58개 중 **25개는 `0x3C..0xF7` 밖**에 있다. 대부분은 진행도·플레이스루 차이지만,
**5개는 옵션 블록으로 보이고 CPP-off 세이브에서는 전부 0**이다.

| offset | off | on | 추정 |
|---|---|---|---|
| `0x13C` | 00 | 03 | ? |
| `0x140` | 00 | 04 | ? |
| `0x15C` | 00 | 02 | ? |
| `0x162` | 00 | **2D** (45) | 카메라 감도? |
| `0x168` | 00 | **40** (64) | 카메라 감도? |

RT37 readme의 *"You can edit sensitivity etc."* 와 맞물려 **CPP를 켤 때 같이
기록되는 감도 기본값**일 가능성이 있다. 그렇다면 기본 프로파일만 적용한 세이브는
**우측 스틱 카메라가 감도 0으로 안 움직일 수 있다.** 반대로 이 5바이트가 그냥
RT37의 개인 설정이면, 쓰는 순간 플레이어 설정을 덮어쓴다.

그래서 강제하지 않고 플래그로 뒀다: `--with-option-block`. §5 A/B 테스트로 결판난다.

헤더의 `0x0E`(`80`→`90`), `0x11..0x12`(`10 42`→`94 21`)도 그룹 상수지만 비트필드가
섞여 있어 어느 비트가 CPP인지 알 수 없다. 두 프로파일 어디에도 넣지 않았다.

## 5. 남은 확인 — 두 가지, 순서대로

### (a) Citra/Azahar A/B — 실기 없이 지금 가능

같은 세이브에서 두 벌을 만들어 각각 부팅한다.

```
python tools/mgs3d_save_tool.py enable-cpp <savedata> -o A_basic.sav
python tools/mgs3d_save_tool.py enable-cpp <savedata> -o B_options.sav --with-option-block
```

보는 것: ① 부팅되는가 ② 게임 내 컨트롤 표시가 듀얼 스틱인가 ③ **우측 스틱으로
카메라가 움직이는가**. ③이 A에서 안 되고 B에서 되면 옵션 블록이 필수라는 뜻이고,
둘 다 되면 기본 프로파일로 확정, 둘 다 안 되면 §5(b)가 필요하다.

**주의: 이 테스트 중에 게임 안 확장 슬라이드 패드 옵션을 열지 마라.** 켜져 있든
꺼져 있든 그 메뉴를 건드리는 순간 먹통이다.

### (b) 실기 CPP off/on 쌍 캡처 — 이게 있으면 추측이 전부 사라진다

지금 실기 검증 중이라면 **2분이면 끝난다**. 이 쌍만 있으면 어떤 바이트가 CPP인지
그룹 차분이 아니라 **직접** 나온다 — 같은 콘솔, 같은 플레이스루라 잡음이 0이다.

1. 실기에서 **CPP를 끈 상태로** 세이브 → Checkpoint(또는 JKSM)로 그 슬롯 백업 → `before.sav`
2. 게임 안에서 **확장 슬라이드 패드를 켜고** 같은 슬롯에 세이브 → 다시 백업 → `after.sav`
3. 두 파일(각 20,768 B)을 주면 끝:

```
python tools/mgs3d_save_tool.py learn-cpp before.sav after.sav -o cpp-profile.json --captured-on "user 3DS"
python tools/mgs3d_save_tool.py enable-cpp <savedata> --profile cpp-profile.json
```

`learn-cpp`는 기본 프로파일 33바이트와 얼마나 일치하는지, 창 **밖에서** 추가로 뭐가
바뀌는지를 같이 출력한다.

RT37의 *"DO NOT turn the CPP back off and on"* 경고는 **에뮬레이터 이야기**다.
실기에는 애플릿이 있고, RT37 본인도 실기(2DS)에서 켜서 그 세이브를 만들었다.
실기에서 토글하는 것 자체는 안전하다.

참고로 서로 다른 콘솔의 세이브를 `learn-cpp`에 넣으면 왜 안 되는지도 확인해 뒀다 —
사용자 CPP-off + RT37 CPP-on으로 돌리면 **110바이트**가 나오고 그중 77개가 창
밖이다(진행도·플레이타임·설정 잡음). 반드시 **한 콘솔에서 나온 쌍**이어야 한다.

## 6. 배포 방침 제안

1. **1순위: 패처.** 진행도 보존, 재배포 문제 없음, 되돌리기 가능. 단 §5(a)가 끝난 뒤.
   최종 사용자에게는 Python 없이 돌아가는 형태(.cmd + 번들 exe)가 필요하다 — 이건
   패키징 결정이라 아직 만들지 않았다.
2. **2순위(보험): RT37 세이브.** 2021년부터 실사용된 검증된 경로다. 동봉한다면
   [`cstick-save-distribution-2026-08-17.md`](cstick-save-distribution-2026-08-17.md)의
   조건 그대로 — `Normal`·`Hard`·`Extreme` 3개만, `readme.txt`와 RT37 크레딧 유지,
   "진행도가 초기화된다" 명시.
3. **어느 쪽이든 README에 이 경고는 반드시 넣는다:**
   > 에뮬레이터에서는 게임 내 **확장 슬라이드 패드(서클패드 프로) 옵션을 켜거나
   > 끄지 마십시오.** Citra/Azahar에 해당 시스템 애플릿이 없어 게임이 멈춥니다.
   > 이것은 한글 패치의 문제가 아니라 원본 게임에서도 똑같이 발생합니다.

마지막 문장이 실질적으로 가장 중요하다. 이 옵션을 건드린 사용자가 **한글 패치를
탓하는 것**을 막아 준다.
