# B. 1.1 standalone — 실기 1차 통과

## 먼저: `analysis/unpacked_1.1`은 순정 1.1 전체가 아니라 업데이트 파티션이다

| | 1.0 | 1.1 |
|---|---|---|
| Program ID | `0004000000081E00` (베이스) | `0004000E00081E00` (**업데이트**) |
| Product code | `CTR-P-AMGE` | `CTR-U-AMGE` (**U** = Update) |
| RomFS | 3,222,482,944 B | **28,672 B** |
| 파일 수 | 924 | **9** |

1.1 RomFS에는 `MGS3D.icn`과 `MGS3D_Release.rsf`뿐 — **게임 데이터가 하나도 없다.**
그래서 "RomFS 전수 diff"는 성립하지 않는다(비교 대상의 우변이 빔). 1.1은 사실상
코드 전용 업데이트이고, 이식 범위는 `code.bin` 하나다.

## 방법론상 함정 하나 (다음 사람도 밟기 쉬움)

세 `code.bin` 모두 **BLZ 압축 상태**다(exheader SCI bit0=1). 압축된 채로 비교하면
패치 한 곳 때문에 스트림 전체가 재배치되어 1.0 vs 한글화가 **513만 바이트/10만 구간**
차이로 나온다. 압축을 풀면 **692 B / 8곳**이다. `tools/nintendo_blz.py`의
`decompress()`를 먼저 통과시킬 것.

## 이식한 것 / 안 한 것

지시대로 **CPP 패치는 제외**했다. 1.1이 enforcer를 재작성해서 1.0의 22 B 패턴이
이미지 전체에 **0회** 존재한다(1.0에서는 1회, 유일). 억지 이식 금지, 1.1 기준으로
새로 분석해 별도 패치로 간다.

| 항목 | 상태 |
|---|---|
| 글리프 훅 6곳 | 이식 완료. 1.1에 동일 인코딩으로 전부 생존 |
| 트램폴린 케이브 | `0x0087F8C4` → `0x008A8104` 재배치 (예약 816 B) |
| `korean_desc` | `0x008E1618` → **`0x009191F8`** 재도출 |
| `font_page_table[2]` | `0x00A46FE0` → **`0x00A87910`** 재도출 |
| blank glyph | `0x0087FBF4` → `0x008A8434` |
| `K = 0x56000` | 상수, 불변 |
| 앨리어스 A4..A7 | 유지 확인 (A0/A3 잔존 0) |
| CPP 패치 | **제외** |

심볼 재도출은 바이트 매칭이 전부 실패했다(1.1이 전역 재컴파일이라 `bl` 변위가
모두 바뀜). `set_font_page`를 앵커로 한 구조 매칭이 유일하게 통했고, **같은 절차를
1.0에 돌려 `0x008E1618`을 되찾는 대조 검증**을 먼저 통과시킨 뒤에 채택했다.
테이블 베이스 `0x00A87908`은 3개 독립 출처가 일치한다.

판정 방법과 전체 근거: `docs/evidence/2026-08-21-stage-unknown-language-adjudication/`
(`RESULT.md`, `resolved-english.csv` 68행).

`DONOR_MISCLASSIFIED` 183(프랑스어/스페인어). 채우면 회귀만 생긴다.

# D. `vox.dat` — 다섯 번째 텍스트 컨테이너 (2026-08-21, 신규)

실기에서 `I think I saw something...`이 영어로 나왔다. stage 169개
`scenerio.gcx`를 리소스 단위로 전수 검색해 **0건**. 실제 위치는

```
romfs/vox.dat   129,990,656 B
sha256          cf9cbd57d1f994bb7103e0281a3a500bf525fe4d943f18bfb86ef0f3d093dd08
레코드 헤더      0x3FC838   텍스트 0x3FC844   len 44 lang 1
```

**clean과 staging이 바이트 동일하다.** 한 번도 건드린 적이 없다. 마스터·워크리스트
CSV 전체에 이 문장은 0건 — 번역 공백이 아니라 **컨테이너 자체가 파이프라인에 없었다.**

## 왜 여태 안 걸렸나

`vox.dat`은 문서에 여러 번 나오는데 전부 "clean과 바이트 동일 = 우리 변경분이
안 건드렸다"는 **안심용 근거**로만 쓰였다. 그게 "번역할 게 없다"로 읽혔다.
124 MB에 이름이 오디오 파일이라 더 그랬다. 실제로는 음성과 자막이 섹터 단위로
인터리브된 아카이브다.

## 레코드 형식 (16바이트 헤더, 리틀엔디언)

```
u32 t0   자막 큐 시작 시각      u16 length  헤더 포함 길이, 4의 배수
u32 t1   자막 큐 종료 시각      u16 lang    1=EN 2=FR 3=DE 4=IT 5=ES 7=EN_ALT
u32 rsv  항상 0                u8  text[]  NUL 종료 + 슬롯 패딩
```

큐는 `(t0,t1)`을 공유하는 연속 레코드 묶음이다. 함정 셋:

- **순서로 큐를 식별하면 안 된다.** EN→ES 3,497개, ES→EN 역순 331개.
- **`(t0,t1)`만으로 묶어도 안 된다.** 타이밍이 블록 간 재사용돼 수백 개가 뭉친다.
- **`lang 7`은 두 번째 영어 슬롯**이다. 큐 맨 앞, 27개 중 22개가 lang 1과 바이트
  동일. 여기를 안 쓰면 영어가 그대로 남는다.

## 파싱에서 잡은 것 둘 — 둘 다 그냥 갔으면 영어가 남았다

**1. 언어 코드를 1~5로 가정했다가 lang 7을 놓칠 뻔했다.**

**2. "패딩은 전부 NUL"을 요구했다가 엔딩 컷신 영어 51줄을 잃을 뻔했다.**
실제 슬랙에는 예전 더 긴 문자열의 잔재가 남아 있다 — `...mission.` NUL `os`.

둘 다 같은 검증이 잡았다: **파일 전체에서 영어 문장처럼 보이는 구간을 훑어
파싱된 레코드 밖에 있는 것을 센다.** 지금 0건. 보조 근거로 다섯 출시 언어가
각각 3,937~3,939개로 나온다(약 3,938 큐 × 5).

구조적으로 유효한 오프셋을 전부 받으면 21,873개에 겹침 2,644개다. 그래서 패딩이
깨끗한 레코드를 seed로 **체인 파싱**한다 — 경계는 인접성이 정하고 추측하지 않는다.

## 수량

```
후보 21,873 → 겹침/미연결 기각 2,133 → 레코드 19,740
  donor(FR/DE/IT/ES) 15,753          ← CSV에서 완전 제외
  영어 3,987 (lang1 3,937 + lang7 50)

```

정상 5언어 큐 3,914 / 전체 3,983. 비정형·제외 96건은 `irregular-records.csv`.

## 산출물 `translation/vox/`

| 파일 | 용도 |

| `vox-translation.csv` | **외부 PC로 가져갈 단 하나의 파일**, 2,691행 |

**왕복 검증 완료.** 4줄 채운 모의 CSV로 `verify` 0 errors, `apply` dry-run
**59곳 전파**(1+14+12+32). 변조 탐지도 확인 — 영문 수정·길이 초과(11>3)·행 삭제는

## 번역 → 적용 (저녁, 완료)

**2,691행 전량 번역되어 돌아왔다.** `verify` 오류 0. 다만 반입 시점에는 **22행이
글리프 16자 부족으로 막혀 있었다** (`쉈 쿨 쑤 엑 썽 옴 쐈 탓 웩 쭤 땡 숴 덟 딨 얌 뺏`).
22행 모두 길이는 통과하므로 막는 건 예산이 아니라 글리프뿐이다. 목록은
`translation/vox/missing-glyphs.json`.

**결정: 글리프를 추가하지 않는다.** 페이지에 89슬롯이 남아 있고 정책이
append-only라 기술적으로는 가능하지만, global page와 stage 169개를 다시 건드리게
되므로 **22행을 기존 character-map만 쓰도록 표현 수정**하는 방향으로 간다.

### 렌더링 확인됨 — 전량 적용 완료

vox.dat 한글 렌더링은 **실기에서 확인됐다.** `Who's that!?` → 누구냐?,
`I think I saw something...` → 뭔가 본 것 같은데. 이 프로젝트에서 vox.dat 자막
경로가 전역 글리프 페이지를 쓴다는 것이 처음 실증됐다.

진단은 두 판이 필요했다. 1차는 `Commence alert formation.` 한 줄이었는데
**occurrence가 많다고 재현이 쉬운 게 아니라서** 확인이 안 됐다(경계 대사가
랜덤). 2차로 사용자가 실제로 목격한 대사 계열(Patrol/HQ 무전 점검 + 발각 대사)
42개 문자열 84곳을 넣자 즉시 확인됐다. **진단 문장은 occurrence가 아니라 관측된
적이 있는지로 골라야 한다.**

### 글리프 부족 22행 — 표현 수정으로 해소

글리프 16자(`쉈 쿨 쑤 엑 썽 옴 쐈 탓 웩 쭤 땡 숴 덟 딨 얌 뺏`)가 없어 22행이
막혀 있었다. **글리프를 추가하지 않고** 기존 character-map만 쓰도록 표현을
고쳐 해소했다. `쿨쿨.`→`드르렁.`, `잘 쐈어!`→`잘 맞혔어!`,
`누가 부쉈어!?`→`누가 부순 거야!?` 등. 전후 기록은
`translation/vox/glyph-rewrites.json`, 원본은
`vox-translation.csv.bak-pre-glyph-rewrite-20260821`.

이 결정으로 **global page와 stage 169개를 건드리지 않았다.** 페이지에 89슬롯이
남아 있고 정책이 append-only라 확장 자체는 가능하지만, 이미 검증된 트리를 다시
흔들 이유가 없었다.

### 줄바꿈 이스케이프 버그 — 실기에서 잡힘, 수정 완료

전량판 1차가 실기에서 `적 발견 N지원 요청`처럼 **줄바꿈 자리에 글자가 찍혔다.**

원인은 도구 버그다. CSV는 줄바꿈을 `
` **두 글자**(백슬래시+n)로 담는데
`encode_korean()`이 실제 개행 문자만 토큰으로 바꾸고 그 이스케이프는 그대로
흘려보냈다. 결과적으로 리터럴 `5C 6E`가 **1,068곳**에 들어갔고 게임이 그걸
그려버렸다. `decode_from_csv()`가 바로 그 용도로 있었는데 `apply` 경로에서
호출되지 않았다.

수정 후 리터럴 `5C 6E`는 1,068 → **213**, 이는 clean과 같은 수이고 파싱된 레코드
텍스트 안에는 **0건**이다(나머지는 오디오 영역, 원래부터 있던 것).

재발 방지로 이스케이프 변환 뒤 **입력 문자열에 백슬래시가 남으면 실패**시킨다.
이 검사를 처음엔 출력 바이트열에 걸었다가 오탐이 났다 — `845C 855C 865C 875C`
네 토큰이 0x5C를 꼬리 바이트로 쓴다(`특`, `꼭` 등). **한글 토큰 안의 바이트를
ASCII로 읽으면 안 된다**는 함정이고, 이 파일 전반에 해당한다.

### 도구에 추가한 안전장치

- `is_text()`가 한글 토큰(0x81~0x87)을 인정 — 자기가 쓴 파일을 재파싱해 검증할 수
  있다. clean 파싱 결과 19,740 불변으로 회귀 없음을 확인했다.
- `extract`가 번역이 채워진 CSV를 덮어쓰지 않도록 거부. 한 번 잘못 돌리면
  2,691행이 사라지는데 사본이 없다.

## 다음 사람이 알아야 할 것

- **한글 렌더링은 실기 확인됐다.** vox.dat 자막 경로도 전역 글리프 페이지를 쓴다.
  이 프로젝트에서 처음 실증된 사실이다.
- **슬롯 예산이 빡빡하다.** `max_bytes` 최소 3 / 중앙값 23. `Ah.` 3바이트,
  `Hmm.`·`Huh?` 7바이트. 한글 1~3자밖에 안 들어가는 자리가 많다.
- **글리프 16자는 끝내 추가하지 않았다.** 22행을 기존 character-map으로 표현
  수정해 우회했다(`translation/vox/glyph-rewrites.json`). global page와 stage
  169개를 흔들지 않기 위한 결정이다. 페이지엔 89슬롯이 남아 있고 정책이
  append-only라 나중에 필요하면 확장 자체는 가능하다.
- **`extract`를 다시 돌리지 말 것.** 번역이 든 CSV를 덮어쓴다. 도구가 거부하도록
  막아뒀지만 `--force`로 뚫린다. 사본은 없다.

# 방법론 메모

Bisection 중 파일 단위 지목 두 건이 틀렸고, 둘 다 증상별로 후보 집합을 저널에서
다시 계산했기 때문에 잡혔다. `r_sna01`/`r_sna02` `scenerio.gcx`는 바이트 동일한데
탐색이 둘을 갈랐고, PROFILE은 소거법으로 `v007a_0`에 도달했다가 반증됐다.

**vox.dat은 세 번째 사례이고 가장 큰 것이다.** 여기서는 *기록 자체가* 교란원이었다.
"clean과 바이트 동일"은 여러 문서에 반복해서 적혀 있었지만 전부 *우리 변경분이
안 건드렸다*는 뜻으로 쓰였고, 아무도 *그 안에 무엇이 있는가*를 묻지 않았다.
무변경 확인은 안전성의 근거이지 범위의 근거가 아니다.

그리고 vox.dat 파싱에서 가정 두 개가 연달아 틀렸는데(언어 코드 1~5, 패딩은 전부
NUL), 둘 다 **음성 검증 하나로** 잡혔다 — "내가 파싱하지 *못한* 영역에 영어가
있는가". 무엇을 찾았는지 세는 것보다 **무엇을 놓쳤는지 세는 것**이 강했다.

**2026-08-21 속편: 두 번 다 "탐색 결과에 처방했다"가 원인이었다.**

r_sna02는 bisection이 지목한 파일 하나에만 수정이 갔고, 스테이지 6,360곳은
분류기가 `english`라 부른 것에만 적용이 갔다. 둘 다 *도구가 자기 판단의 범위를
보고하지 않아서* 오래 살아남았다 — 제외 규칙은 writer에만 있고 게이트엔 없었고,
held 위치는 리포트에 흔적이 없었다. 그래서 이번엔 양쪽 다 **검사와 집계를 추가**했다.
`errors: []`는 "할 일이 없다"는 뜻이 아니다.

**r_sna02 누락은 그 메모의 속편이고 일반화다.** 지목이 교란됐다는 걸 아는 것만으로는
부족했다 — *수정*은 여전히 교란된 지목이 지명한 파일 하나로 갔다. Bisection이
"파일별 결함이 아님"으로 결론나면, 처방은 탐색 결과가 아니라 **동치류 전체**에
적용해야 한다. 값싼 상시 점검: 트리를 내용 해시로 묶어서, clean에서 동일한 파일이
스테이징에서도 여전히 동일한지 확인할 것 — 달라야 할 문서화된 이유가 없다면.

1.1 이식에서도 같은 원칙을 썼다. 훅 6곳과 외부 복귀 타깃 10종을 그룹 시프트로
일괄 환산하지 않고 **하나씩 독립 문맥 매칭으로 확정**했다. 결과적으로 두 시프트로
일관되게 나왔지만, 그건 확인의 결과지 전제가 아니었다.
