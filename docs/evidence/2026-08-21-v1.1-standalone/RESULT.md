# 1.1 standalone 한글 빌드 — 조립 완료, Repack 대기 (2026-08-21)

업데이트 CIA를 따로 설치하는 대신 **베이스 CCI 하나에 1.1 코드를 넣는** 구성이다.

## 왜 이 방향인가

**공식 1.1 자체가 "1.1 코드 + 1.0 RomFS"다.** 업데이트 파티션의 RomFS는
28,672 B / 9파일이고 `MGS3D.icn`과 `MGS3D_Release.rsf`뿐 — 게임 데이터가 하나도
없다. 즉 1.1 코드는 설계상 1.0 RomFS를 상대로 돈다. 그래서 베이스 CCI의 코드만
1.1로 갈아끼우면 기능적으로 등가다.

부수 효과가 크다. **열린 항목이던 "1.1 RomFS shadow" 질문이 소멸한다** —
업데이트 파티션을 쓰지 않으므로 가릴 대상이 없다. 설치 파일도 하나다.

근거로 확인한 것:

- 1.1 코드가 **같은 자산을 참조**한다: `vox.dat` `codec.dat` `movie.dat`
  `demo.dat` 각 1회, `stage` 6회 — 1.0과 동일 (`rom:`만 14→15)
- 1.1 exheader의 **ACI program_id가 이미 베이스** `0004000000081e00`.
  업데이트를 가리키는 것은 `jump_id` 한 필드뿐
- 우리 1.1 패치는 **6개 훅(각 4 B) + 케이브 1구간 = 671 B**. 그 외 무변경

## 왜 exheader와 plain도 1.1이어야 하는가

1.1은 전역 재컴파일이라 섹션 배치가 다르다. 1.0 exheader로는 1.1 코드를 못 싣는다.

| | .text | .rodata | .data | bss |
|---|---|---|---|---|
| 1.0 | 1920p / 7,862,468 | `0x00880000` 58p | `0x008ba000` 92p | 1,460,632 |
| 1.1 | 1961p / 8,028,420 | `0x008a9000` 65p | `0x008ea000` 109p | 1,441,040 |

`plain.bin`도 1.1 것을 쓴다 — 1.1이 서비스 접근 두 개를 추가했다
(`nim:aoc`, `am:app`, 접근 개수 31→33).

## jump_id — 1차는 원본 그대로

exheader `0x1C8`의 `jump_id`는 **1.1 원본 `0004000e00081e00` 그대로 두었다.**
지시대로다. 이 값이 업데이트 타이틀을 가리키므로, 시스템이 그 타이틀을 찾으려 하면
부팅이 실패할 수 있다. **부팅 자체가 안 되면 이걸 먼저 의심하고**, 2차 빌드에서
`0004000000081e00`으로 바꿔 가른다. 그 외에는 건드리지 않는다.

## 알아둘 것

- **CPP 패치가 없다.** 지시대로 1.1 이식에서 제외했고(1.1이 enforcer를 재작성해
  1.0 패턴이 0회), 이 빌드는 **서클패드 프로 지원이 빠진 상태**다.
- **1.1이 무엇을 고쳤는지 우리는 모른다.** 전역 재컴파일과 서비스 2개 추가만
  확인됐다. 얻는 것이 불명확한 채로 CPP를 잃는 교환일 수 있다.
- **세이브 호환성 미확인.** 1.0 기반 세이브가 1.1 코드에서 읽히는지 모른다.
- v0.93a 스테이징은 **무변경**이다
  (`f6da7d858bdf7879fe9a9a454fbc2850b171df760749824a0e27685e99d22d2b`).
  두 트랙이 섞이지 않는다.

## CPP — 정정 (2026-08-21 밤)

**앞서 "코드 패치 불필요 확정"이라고 적었던 것은 잘못된 추론이었다.** 근거가
에뮬레이터 관찰뿐이었고, 관찰된 동작의 원인을 잘못 귀속했다.

### 무슨 일이 있었나

옵션 화면에 CPP가 켜져 있다는 보고를 추적해 Citra 세이브를 읽었다.

```
Citra savedata   gate flag 0x0C bit0 = 1   CPP 테이블 채워짐   scheme 0x13C = 3
Azahar savedata  전부 0 (대조군)
```

그 상태에서 C스틱이 동작했으므로 "1.1이 코드 패치 없이 CPP를 존중한다"고 결론냈다.
**그러나 enforcer 로직을 보면 그건 1.1의 성질이 아니다.**

```
0x0010AEC0  ldr r1,[r0,#8]      ; 게이트 플래그
            tst r1,#1
            beq → preset 0 강제   ; 플래그 꺼짐
            cmp r0,#3 / movne r0,#3 / blne apply_scheme   ; 플래그 켜짐 → preset 3
```

플래그가 서 있으면 **1.0이든 1.1이든 패치가 있든 없든** preset 3으로 간다. 코드
패치는 *플래그가 꺼져 있을 때만* 개입한다. 즉 그 관찰은 1.1에 대해 아무것도
말해주지 않았고, 나는 세이브가 원인인 것을 코드가 원인인 양 일반화했다.

실기에서 CPP가 적용되지 않는다는 보고가 이 오류를 드러냈다.

### 패치의 실제 목적

`mgs3d_cpp_default_patch.py` 도크스트링이 존재 이유를 명시한다 — 게임 내
**확장 슬라이드 패드** 토글이 Extrapad 라이브러리 애플릿(0x408)을 여는데
**Citra와 Azahar가 이를 구현하지 않아 게임이 멈춘다.** 그래서 세이브 편집 대신
enforcer를 패치한 것이다.

**이 패치는 에뮬레이터 우회책이다.** 실기에는 Extrapad 애플릿이 존재하므로 옵션에서
직접 켜는 경로가 살아 있다.

### 해소 (2026-08-21 실기 확인)

**실기 옵션에서 확장 슬라이드 패드를 켜면 C스틱이 동작한다.** 따라서

- **1.1에 CPP 코드 패치를 이식할 필요가 없다.** 실기 사용자는 옵션으로 켠다
- 코드 패치는 **에뮬 전용**이다 — Extrapad 애플릿 미구현으로 토글이 멈추는
  Azahar·Citra 빌드에만 넣는다
- 릴리스 분기 기준은 **기종이 아니라 실기냐 에뮬이냐**다. New 3DS도 실기용 빌드로
  옵션에서 켜면 되므로 별도 빌드가 필요 없다. README와
  `docs/RELEASE-PACKAGING-POLICY.md`를 이에 맞춰 고쳤다

결과적으로 결론("1.1 CPP 코드 패치 불필요")은 처음 적은 것과 같지만, **근거가
달랐고 그 근거는 틀렸다.** 위 정정 절을 남겨두는 이유다 — 맞는 답에 잘못된 이유로
도달한 기록이 지워지면 다음에 같은 추론을 반복한다.

### 다만 배포 기본값은 결정해야 한다

`mgs3d_cpp_default_patch.py` 주석이 **"preset 3은 ZL/ZR과 오른쪽 스틱을 요구하므로
기본 빌드에 넣지 말고 별도 선택 빌드로"** 라고 못박고 있다. preset 3이 켜진 세이브를
구형 3DS/2DS에서 쓰면 **조작이 깨진다.** 기본은 CPP off로 두고 원하는 사용자만
`enable-cpp`를 돌리는 구성이 도구 주석의 취지에 맞는다. 릴리스 시 결정 항목.
