## 3. Reported "x" glyphs (듣, 얼, 마, 임) — investigated, not resolved

All 4 characters **are** present in `character-map.json` with unique,
non-colliding tokens (임=0x8422, 얼=0x84AE, 듣=0x8534 — all in the newer
"global" 0x84xx-0x87xx resident-page range; 마=0x8138 — in the older "static"
0x81xx-0x83xx shared-HPK range, see `wiki/Glyph-System.md`). Checked and
ruled out:

- **Token collision**: none — all 1,120 tokens in the map are unique.
- **Global-page/token-map desync**: none — `korean_token_map_full.csv` (the
  page's own source of truth) agrees exactly with `character-map.json` for
  all three 0x84xx tokens.
- **Blank/corrupted bitmap data**: none — `korean_page_full.bin` has
  substantial non-zero bitmap content at all three glyph indices (26-38
  nonzero bytes of 64), comparable to known-good control indices.

So the character-map data, the page's own token table, and the glyph bitmap
page itself are all internally consistent and non-blank. The remaining
candidate causes are outside what static repo analysis can settle:

1. The renderer trampoline (`code.bin` patches at the 4 points documented in
   `wiki/Glyph-System.md` §3) may have an edge case for specific
   token/index values -- untested beyond the "minimal POC" state that wiki
   section itself flags.
2. The resident page is appended **per stage** `scenerio.gcx` file (169
   files, ~168 distinct hashes since each stage packs only what it needs) --
   if the specific stage(s) where these 4 characters are used didn't get the
   current page appended, only glyphs used on *those* stages would fail
   while everything else works. This is the more likely candidate given 마
   (the one static-range failure) and the three global-range failures don't
   share an obvious token-level pattern.
3. Both mechanisms (191-slot static HPK, 929-slot global page) are declared
   as an all-or-nothing matched set (`dependencies.json`'s own warning: "not
   standalone; both 191-glyph HPKs and this exact combined map are
   required") -- worth checking whether the CCI actually tested had both
   halves from the same build, or a mismatched pairing.

**Not fixed this round.** Left `pending` in `runtime-corrections.csv`.
Root-causing further needs either a live Citra GDB session (see
`wiki/Runtime-Debugging.md`) or a stage-by-stage completeness check of which
`scenerio.gcx` files actually carry the current page -- both are more than a
static-analysis pass, flagging for a decision on how deep to go next.
