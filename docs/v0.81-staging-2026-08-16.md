### Caveat on the 187 proposed lines

These were shortened to fit, preserving the existing wording wherever possible.
They have not had a translator's read. A few source rows carry a Korean line
whose meaning does not match its English (e.g. an `All four of them?` slot whose
Korean was unrelated); for those, fitting necessarily became rewriting, which is
a translator's call rather than a mechanical one. They are in the build so the
next hardware test exercises them, and can be revised in the same one-file loop.

## Open, carried forward

- ~~**`억` renders corrupted after a codec call ends**~~ — **hypothesis refuted
  2026-08-16.** The line is demo record 5 @`11537428`, the *opening cutscene*,
  which precedes any codec call; `11537428` is that occurrence, not an
  alternative location. The next subtitle in the same record (@`11537816`,
  `지금부터 버추어스 미션을 개시한다.`) corrupts `추`/`션` the same way. In both
  lines the broken characters are exactly the global-page ones. Root cause is the
  global-page base, not a post-codec transient. Original text kept below.
- **`억` renders corrupted after a codec call ends** (reported on the v0.80
  build, in a demo/movie subtitle). Data verified clean end to end: character map,
  token map, all 931 page bitmaps byte-identical to a fresh render, and the built
  bytes correct in 63/63 codec units. The reported line has **exactly one
  global-page character (억) and thirteen static ones**, which is the same shape
  as the old codec save-prompt case. Leading hypothesis: right after a codec call
  the anchor global `*(0x008E1618)` still points at the codec object, so
  `obj[0x4C]+0x56000` lands on unrelated memory — a transient stale anchor rather
  than a glyph defect. Cheap check: the same line exists at demo offsets
  `11537428` and `533694288`; if it reads correctly when *not* reached straight
  after a codec call, the hypothesis is confirmed. `code.bin` was not touched.
