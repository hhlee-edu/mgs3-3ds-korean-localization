## 1. 먼저: `unpacked_1.1`은 "순정 1.1 전체"가 아니라 **업데이트 파티션**이다

NCCH 헤더가 명확하다.

| | 1.0 | 1.1 |
|---|---|---|
| Program ID | `0004000000081E00` (베이스) | `0004000E00081E00` (**업데이트**) |
| Product code | `CTR-P-AMGE` | `CTR-U-AMGE` (**U** = Update) |
| RomFS 크기 | 3,222,482,944 B (~3.0 GB) | **28,672 B** |
| 파일 수 | 924 | **9** |

1.1 RomFS 28 KB 안에 든 것은 `MGS3D.icn`(14,016 B)과 `MGS3D_Release.rsf`(1,099 B)
둘뿐이다. **게임 데이터 파일이 하나도 없다** — `codec.dat`, `movie.dat`, `demo.dat`,
`stage/*`, `resident.hpk`, `cache.hpk` 전부 부재.

### 요청하신 "RomFS 전수 diff"가 성립하지 않는 이유

비교 대상이 없다. 1.1이 게임 데이터를 하나도 싣지 않으므로 파일 단위 diff의 우변이
비어 있다. 이건 작업 실패가 아니라 **결과 자체**다: 1.1 업데이트는 사실상 코드 전용이다.

전체 파일 대조는 아래가 전부다.

| 파일 | 1.0 | 1.1 | 결과 |
|---|---|---|---|
| `content.bin` | 8 B | 8 B | 동일 |
| `exefs/logo.bin` | 8,192 B | 8,192 B | 동일 |
| `header.bin` | 512 B | 512 B | 다름 (NCCH 메타) |
| `exheader.bin` | 2,048 B | 2,048 B | 다름 (세그먼트 레이아웃) |
| `plain.bin` | 512 B | 512 B | 다름 |
| `exefs/code.bin` | 5,264,144 B | 5,367,464 B | **다름 — 이번 이식의 전부** |
| `exefs/icon.bin` | 14,016 B | 14,016 B | 다름 |
| `exefs/banner.bin` | 203,792 B | **없음** | 1.1 미포함 |
| `romfs/MGS3D.icn` | 14,016 B | 14,016 B | 다름 (icon.bin과 동일 바이트) |
| `romfs/MGS3D_Release.rsf` | 1,023 B | 1,099 B | 다름 (빌드 설정 잔재) |
| `romfs/` 게임 데이터 920개 | 있음 | **전부 없음** | — |

### 확인이 필요한 미해결 사항 (이식 계획의 전제)

업데이트 파티션의 RomFS가 베이스 RomFS를 **가리는지(shadow)** 아니면 게임이 계속
베이스 RomFS를 읽는지에 따라 결론이 갈린다.

- 베이스를 계속 읽는다면 → 한글화 RomFS 작업(codec/movie/demo/stage 전부)은 **무손실
  이월**되고, 이식 범위는 `code.bin` 하나로 끝난다.
- 업데이트 RomFS가 가린다면 → 28 KB 트리로는 게임이 성립하지 않으므로, 이 덤프가
  불완전하다는 뜻이 된다.

바이트만 보고는 어느 쪽인지 단정할 수 없다. **계획 확정 전에 이걸 먼저 실증해야 한다.**
아래 §4는 첫 번째 경우를 가정하고 쓴 것이다.

## 2. 방법론 정정: `code.bin`은 세 개 모두 압축 상태다

exheader의 SCI 플래그 bit0 = 1 (`compress .code`). 압축된 `code.bin`을 직접 바이트
비교하면 **패치 한 곳 때문에 LZ 스트림 전체가 재배치**되어 무의미한 결과가 나온다.
실제로 순정 1.0 대비 한글화 `code.bin`은 압축 상태에서 5,133,682 B / 102,084 구간이
다르게 나오지만, 압축을 풀면 **692 B / 8곳**이다.

`tools/nintendo_blz.py`로 해제한 결과:

| | 압축 | 해제 | .text 크기 |
|---|---:|---:|---:|
| 순정 1.0 | 5,264,144 | 8,478,720 | 0x0077F8C4 (7,862,468) |
| 한글화 | 5,264,540 | **8,478,720** (1.0과 동일) | 동일 |
| 1.1 | 5,367,464 | 8,744,960 | 0x007A8104 (8,028,420) |

한글화는 해제 크기가 1.0과 **완전히 같다** — 모든 패치가 in-place이고, 코드 케이브도
`.text` 끝 페이지 패딩 안에 들어가 있다는 뜻이다.

세그먼트 레이아웃:

| 세그먼트 | 1.0 | 1.1 |
|---|---|---|
| `.text` | `0x00100000`, 1920p, 패딩 **1,852 B** | `0x00100000`, 1961p, 패딩 **3,836 B** |
| `.rodata` | `0x00880000`, 58p | `0x008A9000`, 65p |
| `.data` | `0x008BA000`, 92p | `0x008EA000`, 109p |
| `.bss` | 1,460,632 B | 1,441,040 B |

`.text`가 **165,952 B (0x28840) 증가**했다. 1.1은 소규모 핫픽스가 아니라 재빌드다.

## 3. 한글화 코드 패치 집합 (문서가 아니라 바이트에서 도출)

순정 1.0 해제 이미지 vs 한글화 해제 이미지 = **692 B, 8곳**. 이것이 이식해야 할
전부이며, 권위 있는 목록이다.

| # | VA (1.0) | 크기 | 정체 |
|---|---|---:|---|
| 1 | `0x0010AEF6` | 21 B | **CPP/C스틱 강제 패치** (`mgs3d_cpp_default_patch.py`) |
| 2 | `0x0015E5A4` | 4 B | 글리프 훅 — `bic r1,r1,#0x6000` → `B 0x0087FB68` |
| 3 | `0x0015E600` | 4 B | 글리프 훅 — `bic r1,r1,#0x6000` → `B 0x0087F8C4` |
| 4 | `0x0015EC58` | 4 B | 글리프 훅 — `bic r1,r9,#0x6000` → `B 0x0087F9C8` |
| 5 | `0x00183A04` | 4 B | 글리프 훅 — `bic r0,r1,#0x6000` → `B 0x0087FB90` |
| 6 | `0x00184398` | 4 B | 글리프 훅 — `bic r0,r0,#0x6000` → `B 0x0087FAC8` |
| 7 | `0x0018445C` | 4 B | 글리프 훅 — `bic r1,r1,#0x6000` → `B 0x0087FB18` |
| 8 | `0x0087F8C4` | 647 B | **트램폴린 케이브** (`.text` 끝 패딩, 순정은 전부 0) |

내역: `692 = 24`(훅 6 × 4 B) `+ 21`(CPP) `+ 647`(케이브). 케이브는 **816 B를 예약**하고
그중 기록이 닿는 폭이 **815 B**이며, 실제로 값이 바뀐 바이트가 **647 B**다(케이브
안에도 0인 바이트가 169개 있고 착지 구역이 원래 0이라 그만큼은 diff에 잡히지 않는다).
변경 바이트로 합산할 때는 647을 쓴다.

케이브 내부의 절대주소 워드 2개 (이식 시 반드시 재해석해야 함):

```
cave+0x320  (VA 0x0087FBE4)  ->  0x008E1618   .data 내부
cave+0x324  (VA 0x0087FBE8)  ->  0x00A46FE0   .bss  내부
```

`0x00A46FE0`은 `docs/global-page-render-path-audit-2026-08-15.md`가 글로벌 페이지
베이스로 지목한 그 주소다.

참고: `docs/RELEASE-PACKAGING-POLICY.md:103`은 트램폴린 범위를
`0x0087F8C4..0x008838C3`(16 KB)로 적고 있으나, **실측은 815 B**이고 1.0 `.text` 패딩은
1,852 B뿐이라 16 KB는 물리적으로 불가능하다. 그 문서 항목은 부정확하다.

## 4. 1.1 이식 매핑

### 4.1 글리프 훅 6곳 — **그대로 이식 가능**

1.1에서 여섯 곳 모두 **동일한 `bic` 명령어**가 그대로 있는 것을 확인했다(주변 문맥
48 B 유일 일치로 위치 확정).

| # | 1.0 VA | 1.1 VA | 시프트 | 1.1의 명령어 | 판정 |
|---|---|---|---:|---|---|
| 2 | `0x0015E5A4` | `0x0015E0A4` | −0x500 | `06 1a c1 e3` | 일치 |
| 3 | `0x0015E600` | `0x0015E100` | −0x500 | `06 1a c1 e3` | 일치 |
| 4 | `0x0015EC58` | `0x0015E758` | −0x500 | `06 1a c9 e3` | 일치 |
| 5 | `0x00183A04` | `0x001817E0` | −0x2224 | `06 0a c1 e3` | 일치 |
| 6 | `0x00184398` | `0x00182174` | −0x2224 | `06 0a c0 e3` | 일치 |
| 7 | `0x0018445C` | `0x00182238` | −0x2224 | `06 1a c1 e3` | 일치 |

훅이 노리는 앨리어스 폴드 로직이 1.1에서도 살아 있다는 뜻이다. **분기 오프셋만
새 케이브 주소로 다시 계산**하면 된다.

### 4.2 케이브 — **재배치 필요, 공간은 충분**

| | 1.0 | 1.1 |
|---|---|---|
| `.text` 끝 VA | `0x0087F8C4` | **`0x008A8104`** |
| 페이지 패딩 | 1,852 B (전부 0 확인) | **3,836 B (전부 0 확인)** |
| 815 B 케이브 수용 | 가능 | **가능 (여유 3,021 B)** |

새 케이브 VA는 `0x008A8104`. 1.0보다 오히려 여유가 2배 넘게 늘었다.

### 4.3 케이브 내부 절대주소 2개 — **재도출 필요**

`.data`와 `.bss`가 통째로 이동했으므로 단순 산술로는 안 된다.

| 대상 | 1.0 값 | 1.0 세그먼트 내 오프셋 | 1.1에서 |
|---|---|---|---|
| `.data` 참조 | `0x008E1618` | `.data` +0x27618 | **재도출 필요** |
| `.bss` 참조 (글로벌 페이지 베이스) | `0x00A46FE0` | `.bss` +0x130FE0 | **재도출 필요** |

`.data` 시작이 `0x008BA000`→`0x008EA000`, `.bss` 크기도 1,460,632→1,441,040으로 줄어
레이아웃이 바뀌었다. 두 심볼이 1.1에서 어디로 갔는지 식별해야 한다.

### 4.4 CPP 패치 (사이트 1) — **유일한 실질 난관, 재분석 필요**

1.0의 해당 21 B와 그 주변 코드가 **1.1에는 존재하지 않는다.** 문맥을 8 B까지 줄여도,
22 B 원본 패턴을 이미지 전체에서 찾아도 1.1 일치 건수는 **0**이다(1.0에서는 1건, 유일).

```
1.0 0x0010AEF6 패턴: 50 e3 04 00 00 0a 00 00 a0 e3 a1 83 00 eb 00 f0 20 e3 00 f0 20 e3
   1.0 내 출현: 1회 (0x0010AEF6)
   1.1 내 출현: 0회
```

즉 1.1은 CPP 강제 로직(`0x0010AEC0`의 enforcer)을 건드렸다. 이 패치는 오프셋 재계산이
아니라 **1.1 enforcer를 처음부터 다시 읽고 다시 써야 한다.**

두 가지 부기:
- 이 패치는 내부 상대 분기(`b 0x0010AEDC`)를 포함하므로 함수 구조가 바뀌면 그대로 옮길
  수 없다.
- `mgs3d_cpp_default_patch.py` 자체 주석이 "preset 3은 ZL/ZR과 오른쪽 스틱을 요구하므로
  **기본 패치에 넣지 말고 별도 선택 빌드로**"라고 못박고 있다. 현재 스테이징 트리에는
  들어가 있다(에뮬레이터 검증용). 1.1 이식 시 이 패치를 **기본 빌드에서 뺄지부터**
  결정하면, 난관 자체가 사라질 수 있다.

## 5. 1.1 코드 이동 규모 (참고)

1.0 `.text`를 64 KB 간격 120지점, 64 B 앵커로 탐침한 결과:

- 앵커가 1.1에 **그대로 남은 지점: 41 / 120**. 나머지 79지점은 64 B 창 안에서 이미 변경.
- 남은 지점의 드리프트는 `0x1E0000`의 **+7,936**에서 `0x800000`의 **+45,980**까지 단조 증가.
- 반면 패치 사이트가 있는 초반부는 **음수**(−0x500, −0x2224) — 국소 재배치가 있었다.

정리하면 1.1은 전역 재컴파일이며, 주소는 어떤 상수 델타로도 환산되지 않는다.
**모든 이식은 문맥 매칭으로 개별 확정해야 한다.** 위 §4.1이 그 방식으로 6곳을 확정했다.

## 6. 재현 방법

`tools/nintendo_blz.py`의 `decompress()`로 세 `code.bin`을 해제한 뒤 바이트 비교한다.

해제 이미지 SHA-256(앞 16):

```
clean10  10c7d3496a864b34    순정 1.0
prodKR   283211e147d54d73    한글화 프로덕션
clean11  68bdf9c5e2436dcb    1.1
```

해제 이미지는 `.text` + `.rodata` + `.data`가 연속으로 붙은 형태이고,
`.text` 구간에서는 VA = `0x00100000` + 파일 오프셋이다. 세그먼트 경계는 §2 표 참조.
