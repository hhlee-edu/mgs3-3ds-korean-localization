# 폰트 리소스 파일 특정 완료 + 3-bank 확장 판정 — 2026-08-12

`docs/font-resource-loader-chain-2026-08-12.md`의 후속. 실행 breakpoint 1회 세션으로
**폰트 리소스 파일을 확정**했고, 그 결과 **3-bank 확장안은 현재 형태로는 불가능**함이
드러났다. 아래 판정 근거를 그대로 남긴다.

---

## 1. 결론 (먼저 읽어라)

| 항목 | 결과 |
|---|---|
| 폰트 리소스 파일 | **`stage/<스테이지명>/scenerio.gcx`** — 스테이지마다 하나씩, 총 91개 |
| 로드 방식 | 파일 **전체를 연속 메모리에** 적재. 라이브 검증됨 |
| 로더 체인 | 정적 분석대로 확정. 런타임 수치까지 일치 |
| **3-bank 확장** | **현재 설계로는 불가.** 폰트가 스테이지별로 다르고 여유 공간이 균일하지 않다 |
| stress 64 POC | **미구현.** 위 판정 때문에 착수 조건이 성립하지 않음 |

**핵심 오해 정정:** "폰트 리소스의 마지막 섹션이 연속 2뱅크(`0x1FE00`)를 담고 있으니
3번째 뱅크를 덧붙이면 된다"는 이전 세션의 제안은 **전제가 틀렸다.** 폰트는 전역 공용
리소스가 아니라 **스테이지별 리소스**이며, 뱅크 2개분 공간이 실제로 존재하지 않는
스테이지가 18개 있다.

## 2. 라이브 검증 (Azahar + GDB, 실행 breakpoint 세션)

### 2.1 폰트 page table `0x00A46FD8`

```text
table[0] = 0x08688578
table[1] = 0x087A973C
table[2] = 0x08982744
table[3] = 0x00000000
table[4] = 0x08992644
table[5] = 0x08698478
table[6] = 0x086A8378
```

`table[4] - table[2] = 0xFF00`, `table[5] - table[0] = 0xFF00`,
`table[6] - table[5] = 0xFF00` — 세터의 자동 파생 동작과 일치.

### 2.2 폰트 descriptor `0x00A472BC`

```text
+0x00 = 0x0892C330      섹션 0
+0x04 = 0x0892C344      섹션 1
+0x08 = 0x089333CC      섹션 2
+0x0C = 0x08982740      섹션 3  ← 폰트
+0x10 = 0x0899FAB2
+0x14 = 0x00000000
+0x18 = 0x00000001
+0x1C = 0x00A472DC
```

**`*(0x00A472BC + 0xC) + 4 = 0x08982740 + 4 = 0x08982744` = `table[2]`** —
정적 분석으로 도출한 공식이 런타임에서 정확히 일치했다. 체인은 확정이다.

보조 descriptor `0x00A472AC`:

```text
+0x00 = 0x0892BE64   ← 버퍼 base + 4
+0x04 = 0x00000132
+0x08 = 0x08982848
+0x0C = 0x089A26C1
```

### 2.3 파일 특정 방법

메모리에서 두 개의 시그니처를 덤프해 romfs 918개 파일과 대조했다.

- **섹션 0 헤더** `14650500 14000000 9c700000 10640500` (16B)
  → **`stage/v001a/scenerio.gcx` 오프셋 `0x4D0`에 유일 일치**
- **폰트 page 2 본문** 34B → **91개 `stage/*/scenerio.gcx` 전부에 일치**

### 2.4 메모리↔파일 매핑 검증

```text
섹션0 메모리 0x0892C330 ↔ 파일 0x4D0
  → 로드 base = 0x0892BE60
page2 메모리 0x08982744 → 파일 0x568E4
시그니처 실제 발견 위치 0x568F2 = 0x568E4 + 14   ✔ 정확히 일치
```

`0x00A472AC[0] = 0x0892BE64 = base + 4` 도 정합. **파일 전체가 `0x0892BE60`에
연속 적재**되며, 로드된 스테이지는 `v001a`였다.

```text
v001a/scenerio.gcx
  파일 크기        489,441 (0x777E1)
  page2 오프셋     0x568E4
  page4 오프셋     0x667E4
  page4 명목 끝    0x766E4
  descriptor+0x10  0x73C52   ← page4 명목 끝보다 앞
  page4 뒤 잔여    4,349 바이트
```

## 3. 3-bank 확장이 불가능한 이유

91개 `stage/*/scenerio.gcx` 전수 조사 결과:

| 측정 | 값 |
|---|---|
| 파일 수 | 91 |
| **서로 다른 page2(뱅크 A) 내용 해시** | **90** |
| **서로 다른 page4(뱅크 B) 내용 해시** | **90** |
| page4 뒤 잔여 바이트 | 최소 **-129,894** / 최대 86,140 |
| **page4가 EOF를 넘어가는 파일** | **18개** |

### 3.1 폰트가 스테이지별로 전부 다르다

91개 중 90개가 서로 다른 내용이다. 폰트는 전역 공용 자산이 아니라
**각 스테이지가 필요로 하는 글리프만 담은 스테이지 전용 묶음**이다.
(이 프로젝트의 기존 "shared glyph allocation" 작업과 같은 모델이다.)

→ 하나의 Korean page를 만들어 한 곳에 넣는 방식이 성립하지 않는다.
   91개 파일 전부에 각각 넣어야 한다.

### 3.2 2뱅크분 공간이 존재하지 않는 스테이지가 있다

18개 파일에서 `page2 + 0x1FE00`이 EOF를 넘는다. 극단적으로
`r_sna01`/`r_sna02`(83,478바이트)는 **129,894바이트 초과**다.

즉 게임은 `table[4] = table[2] + 0xFF00`을 **데이터 존재 여부와 무관하게 무조건
파생**하며, page 4는 상당수 스테이지에서 실재하지 않는 영역을 가리킨다
(해당 슬롯 글리프가 사용되지 않으므로 표시상 문제가 없을 뿐이다).

`v001a`에서도 `descriptor+0x10`(`0x73C52`)이 page4 명목 끝(`0x766E4`)보다
**앞에 있다** — page 4의 마지막 약 10.9KB는 이미 다음 섹션 데이터를 읽고 있다.

→ "page2 + 0x1FE00 위치에 3번째 뱅크를 넣는다"는 **균일한 오프셋 공식이 성립하지 않는다.**

## 4. 이 결과가 배제하는 것 / 남기는 것

### 배제됨

- 폰트 리소스에 3번째 뱅크를 덧붙여 `korean_page_pointer = table[2] + 0x1FE00`로
  끝내는 방식 — **불가**
- 단일 Korean page 파일 하나로 전 스테이지를 커버하는 방식 — 폰트가 스테이지별이므로 불가

### 여전히 유효함

- 로더 체인 자체(§2)는 확정. `*(0x00A472BC+0xC)+4`는 신뢰 가능한 런타임 앵커다
- 파일 전체가 연속 적재된다는 사실 — 파일 끝에 덧붙인 데이터는 **자동으로 resident**가 된다
- 성공한 draw/width trampoline 4개는 그대로 재사용 가능 (pointer 계산식만 바뀜)

### 다음 세션이 검토할 후보 (권장 순서)

1. **스테이지 파일 EOF 추가 + 런타임 base 기준 포인터.**
   버퍼 base는 `*(0x00A472AC) - 4`로 스테이지 무관하게 얻을 수 있다(§2.2 검증됨).
   각 스테이지 파일 끝에 `0xFF00`을 덧붙이고
   `korean_page_pointer = (*(0x00A472AC) - 4) + <해당 스테이지 원본 크기>`.
   → 문제: 원본 크기가 스테이지마다 다르므로 런타임에 알아내야 한다.
     컨테이너 헤더에 총 크기 필드가 있는지 확인할 것(섹션0 헤더 첫 워드 `0x00056514`가
     후보). 있으면 이 방식이 가장 깔끔하다.
2. **스테이지별 Korean 글리프 서브셋 방식.**
   기존 191자 shared allocation과 같은 모델로, 각 스테이지가 실제로 쓰는 한글만
   그 스테이지 폰트에 넣는다. 프로젝트에 이미 도구/데이터가 있다
   (`analysis/shared_glyph_optimized_build_2026-08-12/sna01-allocation-report.json`).
   → 1,119자 전역 커버라는 원래 목표와는 다른 절충안이다.
3. **원래의 신규 RomFS asset + loader 방식으로 복귀.**
   `0x0061D438`이 비동기임은 확정이므로 완료 대기 메커니즘을 찾아야 한다.
   위 두 안이 모두 막히면 이쪽으로 돌아온다.

## 5. 이번 세션의 도구 변경 (추가만, 기존 동작 무영향)

`tools/citra_gdb_mi_controller.py`:

- `--break-at <addr>` (반복 가능): 최초 continue **이전에** 실행 breakpoint 설치.
  부팅 초기에 발생하는 대상을 잡으려면 필수다.
- `--command-timeout <초>`: `send_control`의 3초 고정 타임아웃을 조정 가능하게 함.
- `font-context` 명령: `r4`, `[r4+0x34]`, `[r4+0x4c]`, LR/PC, 스택 프레임 일괄 덤프.

### GDB 실무 메모

- `-break-insert *0x007801DC`는 **정상 등록됐으나 부팅~게스트 125초 동안 미발동**.
  `0x007801B8`은 부팅 경로가 아니다(이전 세션의 setter 캡처에서 LR이 `0x001042B0`,
  즉 `0x001042AC` 경로였던 것과 일치). `0x00108320`은 간접 호출되는 것으로 보인다.
- breakpoint가 안 걸려도 **세션이 살아 있으면 메모리 직접 읽기가 더 확실하다.**
  이번에 파일을 특정한 것도 breakpoint hit이 아니라 라이브 메모리 덤프 + 디스크
  대조였다. 다음에도 이 방법을 우선 고려하라.
